# The demo

A working frontline hiring product. Eleven screens, an overview page, an
assistant you can type at, and a backend that holds all of it.

**Rebuilt 29 August 2026.** Until then this was eleven screens rendering a seed
file, with every number typed in and every button changing a variable in the
browser. It now has a server, a real domain model, a workflow engine, an event
log and an audit trail. What changed and why is in
[../docs/UPDATE_29_AUG.md](../docs/UPDATE_29_AUG.md).

---

## Running it

```
cd demo
node server/index.js
```

Then open `http://localhost:4173`. That is the overview page, which explains the
twenty steps and their four kinds of owner. `app.html` is the product on its own.

There is nothing to install. No bundler, no framework, no package manager, no
`node_modules`. The server is Node's own `http` module and the browser code is
plain JavaScript in classic script tags. That constraint is deliberate and it
should stay.

**It no longer runs from `file://`.** It cannot: the browser holds no data of its
own, and the API key has to live somewhere a browser cannot reach.

One caveat when developing rather than presenting. Browsers cache hard from
localhost and that has produced false measurements repeatedly, including during
this rebuild. If a change looks like it did not take, hard reload before you
believe it.

### Using a model

```
cp server/.env.example server/.env
# then set LLM_API_KEY
```

Everything runs without one. With no key, screening evaluations come from a
deterministic match against the phrase bank the customer owns, and every screen
that shows one prints "No model ran." That is a real feature and it is not a
model, so nothing labels it as one.

The key is read in the server process and never appears in any response.
`/api/llm/status` returns whether one is configured and which model would run,
and nothing else.

## Driving it

| Key | Does |
|---|---|
| `P` | Presenter notes on and off. Then the arrow keys move between scenes |
| `C` | Opens the assistant |
| `R` | Reseeds the whole demo from scratch |
| `T` | Cycles theme |
| `1` to `0` | Jump to a screen, in sidebar order |
| `?` | Keyboard help, and what is currently running |

The sidebar has a clock control: **+4h**, **+1d**, **+3d**. It moves the
simulated present forward and then the ordinary ticker runs. It does not fake
anything. A county court returns because its expected time genuinely passed, an
offer expires because three days genuinely went by. It is the most useful control
in the product for a demo.

**If you are short of time, cut scene 3 or scene 9. Never 5, 7 or 8.** Those are
the decision, the rehire flag and the E-Verify refusal, and they carry the
argument.

## What is real and what is faked

**Real, and running:** persistence across a refresh and a restart. The workflow
engine and the actor rules on every transition. Deterministic eligibility, which
names the rule that failed and the values it used. The rehire lookup and the
three-year I-9 window. Every duration and count, computed from recorded events.
The compliance clocks. The adverse action bar, which refuses the product's own
user with the reason. The audit trail, including refusals. The assistant's tools,
against the live database. The model call, when a key is set.

**Synthetic, which is not the same as mocked:** the retailer, five stores, eight
requisitions and thirty-six people, all invented. Sunfield Markets does not
exist. It is deliberately mid-market rather than big-box, because big-box is a
different problem. The data is made up; what happens to it is not.

**Simulated, and labelled on screen:** every connector. Job boards, the screening
agency, I-9 and E-Verify, payroll, the identity directory, scheduling and
training. None holds a credential and none names a vendor we have integrated. The
adapter registry has no vendor field to fill in, which is what makes "Connected
to Workday" impossible rather than merely discouraged.

**Development adapters:** email and SMS. Messages are composed, recorded with a
provider reference and a delivery status, and never leave this machine. Outbound
voice is an interface rather than a running integration, and the record says so.

**Sourced:** the legal deadlines, verified against eCFR, e-verify.gov, uscis.gov,
the Federal Register and state statute on 16 Aug 2026. Counsel sign-off is still
required before any of it enters a PRD.

Two honest caveats also stated in the code. Business-day arithmetic counts Monday
to Friday and ignores federal holidays, whereas real E-Verify deadlines run in
federal government working days which do exclude them. And the screening
conversation is synthetic: the answers come from the seed, because we do not have
a real retailer's applicants to ring up. Everything done to that conversation is
real.

## Testing

```
sh tools/test.sh
```

Three parts. The server suite, an end-to-end walk against a real running server,
and the assistant's three case suites.

| Suite | Current |
|---|---|
| Server: data, workflow, model, agent, safety | 62 of 62 |
| End to end, including a restart | 2 of 2 |
| `cases-training.json`, regenerated from the intent table. In sample, so 100% is the floor | 133 of 133 |
| `cases-heldout.json`, paraphrases that appear nowhere in the intent table. The only number that measures generalisation | 32 of 32 |
| `cases-safety.json`, must-not-fire cases, plus four that must fire to catch over-blocking | 57 of 57 |

**Run them after any change to the workflow engine, the tools or the classifier.**

The safety suites exist because they keep finding things. Rebuilding the
assistant's suite once uncovered six ways it would carry out an action it had
only been asked about. Growing it from 43 cases to 57 during this rebuild found
two more: a singular send acting on one of two named people, and a request to
"clear out everyone under 50" resolving to a bulk *approval* of the weakest
candidates.

Traps recorded so nobody rediscovers them the hard way:

- Lowering the fuzzy-match threshold on concepts costs nine cases, because
  "fire" is one edit away from "hire".
- A person-name fuzzy match landing just under the gate approves **nobody**
  rather than the wrong person, which looks like a pass and is not.
- A runner-up intent that could never fire, because it needs a person and none
  was named, used to eat the margin and take a valid question down with it.

The browser layer is `tools/e2e.spec.js`, which needs Playwright. This repository
installs nothing, so it is opt in:

```
npx playwright test tools/e2e.spec.js --browser=chromium
```

`server/test/e2e.test.js` walks the same journey through the API with no
dependencies and runs as part of the normal command.

## The assistant

Twenty-seven intents, seventeen tools, and one rule that makes the rest work:
**both routes end at the same tool registry, and the tools are the only thing
that can change data.**

With no key, `js/nlu.js` picks the intent. It runs in the server process, loaded
from the same file the browser and the test harness use, so there is one
classifier rather than three copies. With a key, the model is given the same tool
schemas and picks for itself. A safety rule written into the tool layer holds
either way, which a safety rule written into a prompt does not.

Three confirmation levels. Reading answers and stops. Anything that changes
something or sends something outside asks first. A hiring decision asks too, and
the confirmation *is* the human act: it is recorded as the named person
approving, via the assistant, at that time.

There is no bulk reject tool. A wrong bulk approval is fixed by a conversation. A
wrong bulk rejection is not fixable at all.

Under every reply there is a line you can open showing which route answered,
which tool ran, what it matched on and how confident it was. The point is that it
can be audited rather than trusted.

## The design language

Unchanged, and it should stay that way. Springs rather than fixed-duration
transitions, so motion can be interrupted. Numbers count up when a screen lands.
Sheets slide from the right for detail.

Four colours, and each one means an owner rather than a mood: purple for the
agent, blue for a person deciding, slate for deterministic software with no
judgement in it, amber for a wait nobody can compress. Green is not an owner and
appears only where something genuinely finished.

No gradients, no decorative green, no arrows inside filled buttons, no AI
sparkle. The product should look like serious enterprise software.
