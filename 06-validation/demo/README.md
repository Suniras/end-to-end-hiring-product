# The demo

A working demo of the frontline hiring product, built against the spec in
[../demo-spec.md](../demo-spec.md) and the decisions in [../../DECISIONS.md](../../DECISIONS.md).

## How to run it

**Double-click `index.html`.** That is the whole instruction. There is no build step, no install, no
server and no network requests. It is plain HTML, CSS and JavaScript with the fonts inlined, so it works
offline and from a file path.

If you would rather serve it over http, for example to share it on a local network:

```
python3 -m http.server 8000 --directory 06-validation/demo
```

Then open `http://localhost:8000`. Python is already on the machine, so nothing gets installed.

**One thing to know if you edit it.** Browsers cache CSS aggressively over http. If you change a
stylesheet and the page looks unchanged, hard reload with Cmd-Shift-R. This does not happen when you open
the file directly.

## The design language

Not an imitation of NuAnchor. The same tokens.

The colour values in `css/tokens.css` from `--bg` through `--warn-soft` were extracted from the NuAnchor
demo pack in `00-context/nuaisle-v0.0/`, which states in a comment that it lifted them from the live
product at nuanchor.nustack.tech. Same names, same values, same three-state theming. The two variable
fonts were extracted from the same file, so the typography is identical too.

Four things were added, only where NuAnchor had no equivalent: a critical state, a fixed-wait state, a
deterministic-software state, and the space, radius and motion scales.

**The one idea worth understanding.** NuAnchor ships a dedicated `--agent` purple that is separate from
its `--accent` blue, so machine action and human action are different hues. This demo extends that to four
owners, taken straight from `05-strategy/automation-breakdown.md`:

| Token | Hue | Means | Breakdown category |
|---|---|---|---|
| `--agent` | purple | a model does this | B |
| `--accent` | blue | a person decides this | C |
| `--system` | slate | deterministic software | A |
| `--clock` | amber | a fixed wait nobody owns | D |

So the colour system is the analysis. The waits are deliberately unsaturated because nobody owns them.

Interaction follows the Apple guidance: springs rather than fixed-duration easing, so motion starts from
the current on-screen value and can be interrupted; feedback on pointer-down; translucent chrome with
content scrolling under it; size-specific letter-spacing; and `prefers-reduced-motion`,
`prefers-reduced-transparency` and `prefers-contrast` all honoured.

## What is real and what is faked

**Real, and running in the browser in front of you:** the twenty steps and their owners, the
business-day arithmetic behind every compliance clock, the refusal when you try to remove a contested
new hire's shift, the state changes when you hire somebody, the audit entries, and the funnel maths.

**Invented:** the retailer, every store, every person, every count and every duration. Sunfield Markets
does not exist. It is deliberately mid-market rather than big-box, because big-box is outside our target.

**Simulated, and labelled as simulated on screen:** payroll, workforce management, the identity
directory, the screening agency, E-Verify, and the learning system. Per D-018, no real integration
exists.

**Sourced:** the legal deadlines, verified against eCFR, e-verify.gov, uscis.gov, the Federal Register
and state statute on 16 Aug 2026. The full table with URLs is in
[../../05-strategy/integration-surface-map.md](../../05-strategy/integration-surface-map.md) section 5.
Counsel sign-off is still required before any of it enters a PRD.

Two honest caveats that are also stated in the code. Business-day arithmetic here counts Monday to Friday
and ignores federal holidays, whereas real E-Verify deadlines are in federal working days which do exclude
them. And the voice screening call is shown as a log rather than dialled live, because Nurix has already
shipped a live voice screening agent on the aviation build, so showing one recorded call is the honest way
to demo a capability that exists without dialling a phone on a call.

## How it was tested

Driven with a real browser rather than eyeballed. Fifteen checks, all passing: every route renders, every
view's content is reachable by scrolling, no button renders as an unstyled div, hiring somebody moves the
pipeline counts, the shift-removal refusal fires and explains itself, the step detail panel carries its
legal text, presenter notes step through all ten scenes and land on the store seat, reset restores the
opening state, and both themes paint their own ground.

Two real bugs were caught that way and are worth knowing about, because both were invisible and neither
threw an error. Buttons built with more than one variant class were silently rendering as unstyled `div`s
with no keyboard focus, because the DOM helper's selector parser rejected the space. And the app shell
pinned itself to the viewport height with `overflow: hidden` while leaving the grid row set to `auto`,
which clipped everything below the fold instead of scrolling it, making the bottom of six screens
unreachable.


## The assistant

A floating button, bottom right, or press `C`. The panel grows out of the button and shrinks back into it,
so it comes from the thing you pressed.

### What it is, and what it is not

**It is not a language model and it must not be described as one.** It is an intent classifier that runs
entirely in the browser. There is no network call, no API key and nothing to bill. Its job is narrow: take
what somebody typed, work out which of eighteen fixed intents they meant, pull out the people and stages
involved, and tolerate paraphrase, word order, plurals and typos.

So it handles "hire alicia", "can you please approve alicia reyes", "lets go ahead with alicia" and
"aprove alica" as one intent. It cannot answer a question nobody wrote an intent for, and it will say so
rather than guess.

### How it decides

Nine steps, in `js/nlu.js`:

1. Normalise: lowercase, expand contractions, spelled-out numbers to digits, strip punctuation.
2. Tokenise, dropping stopwords but **keeping negations**, because "do not approve" and "approve" must never
   collapse into the same thing.
3. Fold surface forms onto concepts with a synonym table. The classifier never sees "greenlight", it sees
   `HIRE`. This is where paraphrase tolerance actually comes from.
4. Light suffix stemming, no external library.
5. Score concept overlap weighted by inverse document frequency, so a concept appearing in one intent counts
   for far more than one appearing in ten.
6. Bonus for multi-word phrases, matched with a small gap allowed. English separates verb particles
   constantly: "take kayla off the rota" has to match the phrase "take off", and contiguous-only matching
   misses it.
7. A fuzzy Damerau-Levenshtein pass, but only for tokens that matched nothing. That is what catches typos.
8. A per-intent gate. Some intents require a concept to be present at all, so "remove her shift" cannot be
   scored as "show me shifts". Entities can satisfy a gate: somebody asking "why is sasha taking so long"
   never types the word "check", but Sasha is a background check.
9. Confidence, as the top score over the sum of all scores, plus the margin over the runner up. Below either
   threshold it asks rather than guessing.

### The three rules its handlers follow

**An action that changes something asks first.** Reading does not. Approving somebody shows the score, the
band and the wait, then asks. Only then does it commit, and it records who decided.

**An action the law forbids is refused with the reason.** Ask it to take Kayla off next week's rota and it
refuses, explains that removing a scheduled shift is an adverse action while she contests an E-Verify
mismatch, shows the remaining working days, and logs the attempt to the same refusal log the store manager's
attempts appear in. That refusal reads live case state rather than a hardcoded flag, so it lifts by itself
when the case closes.

**Every reply can show its working.** Each answer carries a collapsible line with the matched intent, the
confidence, the margin, the concepts it matched and the exact words it matched them on, with fuzzy matches
labelled as fuzzy. A reviewer should be able to audit the classifier, not just trust it. That disclosure is
the most useful thing in the panel when somebody sceptical is watching.

### What it will refuse or decline

Worth knowing before demoing it, because these are the interesting cases:

- Removing a contested employee's shift. Refused, explained, logged.
- Approving somebody matched to a do-not-hire record. Refused, with a route to the review screen.
- A negated request such as "do not approve ryan". Nothing happens, and it says why.
- Firing an employee, changing pay, emailing a candidate, deleting records. All out of scope, so it declines
  rather than reaching for the nearest similar action.
- Anything it matched with low confidence. It offers its top two guesses instead of acting.

### How it was tested

`tools/nlu-harness.js` runs a JSON list of `{text, expect}` cases headlessly against the classifier:

```
node tools/nlu-harness.js cases.json
```

Three suites, in increasing hostility.

| Suite | Cases | Result |
|---|---|---|
| Its own training utterances | 91 | 91 correct |
| A held-out paraphrase set, written without looking at the vocabulary | 28 | 28 correct |
| An adversarial set: terse, verbose, misspelled, out-of-scope, jargon and deliberately ambiguous | 364 | 278 correct, 76% |

The adversarial set was generated to attack it, and it did. It started at **53.6%**. Roughly a third of its
cases are things the product cannot do and must decline, which is the whole point: an assistant that helpfully
guesses is worse than one that admits its limits.

**The number that actually matters is the unsafe-misfire count, and it is 2 of 364.** An unsafe misfire is a
request that should be refused but comes back as an action. Both remaining ones resolve to "approve" with
nobody named, which the handler answers by asking which candidate rather than by approving anybody.

### The bugs that testing found

Every one of these was invisible without measurement, and none threw an error.

**Structural, found by the paraphrase suite:**

- A multi-word concept surface was also indexing its individual tokens, so "drop off" in the reports concept
  taught the classifier that "drop" meant reports. "Drop kayla from the rota" resolved to a metrics query.
- Phrases only matched contiguously, so "take off" never fired on "take kayla off the rota". That broke the
  single most important intent in the product.
- A possessive scored 0.708 against a person-match threshold of 0.72, so "kayla's case" found nobody. The
  underlying cause was that trimming apostrophes only at token boundaries left the one inside "kayla's" intact.

**Safety, found by the adversarial suite. These are the ones that would have ended a demo:**

- **No out-of-scope vocabulary existed at all.** The classifier always picked whichever of the 18 intents
  matched best, so a request it could not fulfil landed on the nearest thing it could. "Email Kayla her FCRA
  letter" answered as though it had sent the letter. "Bump Owen Pike's comp to 17 an hour" answered with a
  background check. 37 cases.
- **Questions executed as commands.** "Who approved Alicia" returned approve at full confidence. A question
  answered by hiring somebody.
- **Ordinary politeness killed real requests.** Negation was a global flag, so "if it is not too much trouble,
  push Marcus through" was discarded entirely. Negation is now scoped to a few tokens around the action verb.
- **"Green light Marcus Hale" changed the theme,** because bare "light" was a theme surface.
- **"Approve everyone above 75 except Ryan" would have approved Ryan.** A bag of concepts cannot represent an
  exclusion, so exclusions, undo requests and bulk rejections are now hard-blocked rather than scored.
- **Confidence was 1.0 whenever exactly one intent survived the gate,** by arithmetic, however little evidence
  there was. "Unblock trevor" scored 1.0 on an empty concept list. A prior in the denominator fixed it.

### One fix deliberately not made

The obvious remedy for "hier alecia" is to relax the fuzzy-match threshold, because a single transposition in a
short word falls just under it. That was measured and it costs nine cases, because **"fire" is one edit from
"hire"**. "Fire alicia" would become an approval. Common misspellings are handled by an explicit map instead.

### Running the suites

```
node tools/nlu-harness.js cases.json
```
Takes a JSON array of `{text, expect}` and prints the pass rate plus every failure with its confidence,
margin, alternatives and matched concepts.
