# API reference — the two-generation REST surface

## Method note (grade this precisely, per discovery.md guidance)

Each **individual v2 Hire endpoint page** (`get_v2-applicants-id.md`, `post_v2-webhook-settings.md`,
etc.) embeds a **verbatim, parseable OpenAPI 3.0.1 fragment** (`"openapi": "3.0.1", "info": {"title":
"Hire Public API", "version": "v2"}, "servers": [{"url": "https://api.fountain.com", ...}]`) inline in
the page body — confirmed by fetching two sample pages in full. This is `method: openapi-verbatim`,
**confidence: high**, for the v2 Hire API family (108 pages). No single combined `openapi.json` was found
served at a guessable root path — each page carries its own operation-scoped fragment — so reconstructing
the *complete* v2 spec means concatenating all 108 fragments (not attempted here; digested instead).

The **microservice (`service*`) family** (~537 pages) is **LoopBack-generated documentation** (see
below) — these pages are titled generically ("find one X", "count Y") and follow LoopBack's
autogenerated-doc idiom exactly; not independently confirmed as carrying embedded OpenAPI fragments the
way v2 pages do (not fetched for this run — flagged as an open question / a cheap follow-up: fetch one
`service*` page raw and check for the same embedded-JSON pattern).

## Notable technology signal: LoopBack framework (backend fingerprint)

Every `service*`-prefixed endpoint description uses **verbatim LoopBack filter-query syntax**:

```
filter[where][fieldName][eq]=value
filter[where][and][0][fieldName1][eq]=value1&filter[where][and][1][fieldName2][eq]=value2
filter[limit]=25&filter[skip]=25
filter[fields][fieldName1]=true&filter[fields][fieldName2]=true
```

This is the **LoopBack 3/4 (Node.js) framework's** idiomatic REST filter grammar — a strong, direct
backend-technology fingerprint independent of any other dimension (a docs-level observation, not an
inference from bundle/DNS). Resource-naming conventions (`count X`, `find one X`, `find many X`,
`replace one X which exists or not`, `partially update`) match LoopBack's auto-generated CRUD-explorer
doc titles almost verbatim, suggesting these ~537 pages were **mechanically generated from a LoopBack
service's introspected model+datasource definitions**, not hand-written.

## An MCP tool-exposure tag, in the wild

The `Get Applicant Info` (`GET /v2/applicants/{id}`) OpenAPI fragment carries:

```json
"tags": ["Applicants", "exposeAsMcpTool"]
```

This is direct, verbatim evidence that Fountain tags select v2 endpoints for exposure as **MCP tools** —
i.e. there is an internal mechanism converting a subset of the public REST API into MCP tool
definitions. This corroborates/extends the recon-plan's agent-skill-manifest finding: Fountain is
building **two** distinct agent-facing surfaces — (1) the `.well-known/agent-skills` docs-discovery
manifest (points an agent at `llms.txt`) and (2) an `exposeAsMcpTool`-tagged OpenAPI operation set (points
an agent at live tool-callable endpoints). Only one tagged operation was directly observed in this pass
(sample size: 2 pages fetched in full); the full extent of `exposeAsMcpTool`-tagged operations is an open
question for the `api` dimension to enumerate (would need to fetch all 108 v2 pages, or find an MCP
manifest endpoint directly).

## v2 Hire API — the legacy ATS surface (108 endpoints)

Core resources: **Applicants** (CRUD, advance/bulk-advance, transition history, duplicates, notify,
secure-document upload/link/approve/reject, SMS messages, notes, labels, GDPR-anonymize with/without
whitelist, async PDF print-request), **Funnels/Openings** (== "Opening"; funnel and opening are used
interchangeably) + **Stages**, **Hiring Goals**, **Location Groups** / **Locations** (each attachable to
Company Attributes), **Positions**, **Option Banks**, **Data Keys**, **(Timestamped) Exports**, **Roles**,
**Shifts**, **User Activities**, **Users**, **Webhook Settings** (14 event types — see raw/webhooks.md),
**Workers** (activate/deactivate, tied to Posthire), **Workflows** (list/delete; a workflow-reassignment
endpoint is explicitly marked **Alpha**, gated behind an account flag, "reach out to your account
representative").

### Sample schema depth — the `Applicant` object (from the verbatim OpenAPI fragment)

The `Applicant` schema is large and reveals the product's real data surface:

- **PII/compliance fields** (a large explicit "Secure Fields" allowlist, excluded from the default GET
  response unless specifically requested): SSN, gender, ethnicity, citizenship, `can_work_in_us`,
  religious preference, full income/tax detail, driver's license, passport, bank account/routing/IBAN/BIC,
  vehicle registration, W-4 federal/state forms.
- **I-9 + E-Verify embedded directly on the applicant record** — `i9` (structured form fields incl.
  preparer/translator info), `i9_status` (state machine: `awaiting_employee → awaiting_employer → pending
  → complete`, plus `opted_out` / `awaiting_authorized_representative`), `everify` (case_number,
  case_status enum incl. `PHOTO_MATCH`, `MANUAL_REVIEW`, `FINAL_NONCONFIRMATION`).
- **Background-check vendor abstraction**: `background_checks[]` is a tagged union of **Checkr** and
  **Onfido** shapes (`vendor: "checkr" | "onfido"`) with per-vendor status enums.
- **E-signature vendor abstraction**: `document_signatures[]` supports **HelloSign** and **DocuSign**
  (`vendor` enum).
- **Training/LMS integration**: a `lessonly` object (Lessonly lesson/path completion results) — a named
  third-party integration embedded directly in the core Applicant schema, not just a webhook payload.
- **Async video interview**: `video_url_objects[]` ties a video URL to a `question_id`/`label` — "async
  video screening" is a first-class, schema-level feature, not a bolt-on.
- **`partner_data[]`** — explicitly documented as "Partner-specific data... value is an array... the
  completed package object will only have keys `statuses` and `details`." The doc's own example partner
  name is **"AI Interview"** — direct evidence of a named third-party AI-interview partner integration
  slot in the schema (not Fountain's own AI, a partner's).
- **Granular consent fields** (`consent_sms_transactional`, `consent_sms_marketing`,
  `consent_calls_transactional`, `consent_calls_marketing`, each with an `_at` timestamp, tagged with an
  internal ticket ID `AXHE-3408` in the description) — TCPA-driven compliance engineering, dated/tracked.
- **Assessments** — a generic `assessments[]` array (score, system_type, file_url) — a pluggable
  pre-hire assessment slot.

### `WebhookSetting` schema

`type` (string, one of 14 enumerated webhook types — see raw/webhooks.md), `url`, `disabled`,
`authorization_method` (`no_auth | simple | oauth`), `authorization_header`, `send_secure_data` (boolean
— an explicit opt-in to include PII in webhook payloads).

## The 12 microservices ("Fountain One") — see raw/doc-map.md for the full per-service endpoint-count table

Digest of what each service's resource model implies about the product suite (from resource names +
descriptions only — no schemas fetched for these, `docs-reconstructed`, confidence medium):

- **serviceattendance** — a full WFM (workforce management) module: shift creation/publish/versioning,
  timesheets with clock-events, time-off requests, holiday-rule + automatic-break-rule + worker-request-
  rule engines scoped to a location or location-group, demand-based bulk shift generation, "timesheet
  flag rules." This is a materially deeper scheduling/attendance product than a typical ATS bolt-on.
- **serviceworkforce** — the core worker/job/location registry underlying both Hire and Onboard/Posthire.
- **serviceorganizations** — the tenancy model: companies, brands (multi-brand support per company), EINs
  (multiple tax entities per company — franchise/multi-employer support), company attribute *sets*.
- **servicetodo** — the "Onboard" task-flow engine, PLUS a **Copilot task-flow authoring lifecycle**:
  `createForCopilot` → `cloneForCopilot` (draft→test) → `publishForCopilot` → `applyTestChangesToDraft
  ForCopilot` → `deleteForCopilot`, paired with `copilotAuditLogs` (in serviceorganizations). Read as a
  **draft/test/apply pattern with an audit trail** — i.e. an AI agent proposes a task-flow, a human tests
  and reviews it before it's applied to production, with every step logged. This is the strongest direct
  evidence available in docs for the "Cue" workflow-automation-AI-agent marketing claim being a genuine
  AI-authoring loop rather than a relabeled rules engine — though it stops short of proving the
  underlying model/architecture (still an inference from API shape, not a session observation).
- **servicepulse** — an employee-engagement / pulse-survey product (surveys, question banks, themes,
  participants, notification templates) — plausibly the backend for the "Sam" retention AI agent
  marketing claim, though nothing in the docs ties `servicepulse` to an "AI-driven" retention loop
  specifically (the survey CRUD itself is generic).
- **servicepool** — a talent-pool/CRM layer distinct from the ATS: `talent`, `audiences`, `unifiedJobs`,
  and — notably — **`GET .../talents/{id}/jobmatches`: "Find unifiedJobs matches for a given talent based
  on aggregate vector match"**. This is direct evidence of **embedding/vector-similarity-based job
  matching**, a genuine ML feature (not just marketing language) sitting in a real, documented endpoint.
  Also carries its own Copilot-authored-audience endpoints.
- **serviceemployment** — employment/compliance profile management (W-4/I-9 document assignments,
  employer notes, tags, "rehire/restart a profile submission") — the back-office side of the Applicant
  schema's I-9/W-4 fields.
- **servicemedia** — file storage abstraction over presumably-S3 (`edm`, `attachments`, `csvimports`
  buckets by name), presigned-upload flow, e-signature document retrieval (`signDocs`).
- **servicesecurity** — API-key issuance/OAuth token minting, `opensignups`, worker/employer
  **impersonation URL** generation (used by "Embedding the Worker Portal" — see integrations doc), and a
  "One stop setup for PAPI" endpoint (**PAPI** likely = "Partner API," tied to `hirePapiProfile` seen in
  the Universal Tasks Webhook payload — an open question, not confirmed by name expansion anywhere in
  docs).
- **servicecompliancev** — document-type/requirement/submission tracking with **Atlas Search** named
  explicitly ("Search workerComplianceProfiles (Atlas Search)") — a direct MongoDB Atlas Search
  fingerprint, i.e. this service's datastore is very likely MongoDB Atlas.
- **servicereferral** — an employee-referral program with campaign targeting against openings.
- **servicestaff** — employer registry (distinct from `serviceorganizations` companies — "employer" here
  reads as a legal/staffing-agency-side entity, given the "delete with slot reassignment" operation,
  consistent with a staffing/gig-worker-slot model).
